---
name: guard-bootstrap
description: Analyze a target repository and configure a Guardrails V3 profile that can generate and verify an independent .NET gate.
---

Read the V3 `README.md`, `DEPLOYMENT.md`, rule contract and technical design. Run `Invoke-V3Setup.ps1 -Mode Analyze` against the target repository, excluding copied guard packages and fixtures, then review its evidence with the actual project structure, build/test commands, existing policy authorities and CI jobs. Use `-Mode Init` for an unreviewed profile outside the reusable example, or update a target-specific profile already present. Put technology and focused commands in `tech-stack.json`, areas/owners/risk triggers in `project-map.json`, and one rule JSON per stable ID. Treat analysis proposals as candidates; confirm all policy values against repository evidence and maintainers. For each candidate rule, state what the supported detector proves and misses; use `kind: none`, `advisory`, `coverage: none` when no detector exists. Never label a prose-only rule blocking.

Run `Invoke-V3Docs.ps1 -Mode Render` and `-Mode Check` to produce the readable profile index, map, tech stack, rules and stage coverage. Keep JSON authoritative; for semantic Markdown edits, use `-Mode Import` to preview and `-Apply` only after reviewing the source hash and proposed JSON. Keep rationale in separate notes. Run `Validate`, `Generate`, `Check`, and the generated `Test` in an isolated target or output directory. Verify compliant and deliberately violating fixtures for each blocking detector. Keep target-specific profile files and generated trial output separate from the reusable V3 default package. Report unsupported rules, required host-specific CI/Skill/Hook installation, and whether required merge checks are actually configured. Do not change an existing production gate as a side effect of bootstrapping V3.
