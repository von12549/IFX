# IFX all-module Inbound Adapter target (proposal)

This is a **future architecture proposal**, not the current IFX policy or a blocking rule. The optional ArchUnitNET pilot checks only the already-valid CRM Domain-to-Contracts type boundary. The independent LayerGuard and CI continue to enforce the present architecture.

The intended provider path is `external caller → public Contracts interface → provider Infrastructure/Inbound adapter → Application use case`. Composition registers the public interface to the Inbound adapter. The Application use case takes application-owned input and returns application-owned output; the adapter performs protocol/version/context conversion. Consumer modules keep outbound adapters in their own Infrastructure. Behavior tests must check DI resolution, validation order, tenant context and authorization; compiled architecture checks cannot establish those outcomes.

| Module | Current public surface and provider | Proposed migration |
| --- | --- | --- |
| CRM | `IAccountComplianceContract` in `CRM.Contracts.V1`; `CRM.Application.Contracts.AccountComplianceContract` implements it, and Composition registers it | Add `CRM.Infrastructure.Inbound.AccountComplianceAdapter`; call an Application-owned compliance use case; move registration to the adapter; remove Application's own public Contracts dependency after behavior parity. |
| Registry | `IClassSubscriptionAvailabilityContract` in `Registry.Contracts.V1`; `Registry.Application.Contracts.ClassSubscriptionAvailabilityContract` implements it | Add `Registry.Infrastructure.Inbound.ClassSubscriptionAvailabilityAdapter`; delegate to an Application-owned use case and update Composition. Treat `ClassStatusChangedV1` as a separate event contract. |
| IAM | `IResourceAuthorizationContract` in `IAM.Contracts.V1.Authorization`; `IAM.Application.Access.ResourceAuthorizationService` currently implements both internal and public interfaces | Split the public wrapper into `IAM.Infrastructure.Inbound.ResourceAuthorizationAdapter`, retaining the Application authorization service behind an internal port; update Infrastructure/Composition registration and consumer tests. |
| Transaction | Public `TransactionProcessedV1` event contract; Application references Transaction.Contracts to publish it | Keep the public event schema stable, introduce an Application-owned event intent and map/publish it in Infrastructure. Do not infer that an Inbound interface is needed until an actual public synchronous provider contract is identified. |
| Holdings | No module-owned public Contracts project in the current source tree; Infrastructure consumes Registry, Transaction and IAM contracts through outbound integration adapters | Preserve those outbound adapters. Add an Inbound provider only if Holdings publishes a reviewed public interface later; require explicit nonempty scope before any implementation-location rule. |

For synchronous provider interfaces, a future target profile should declare **every** provider Contracts, Application and Infrastructure assembly in its manifest, require concrete public-interface implementations in the matching `Infrastructure.Inbound` namespace, and reject Application-to-own-public-Contracts dependencies at both project and compiled-type levels. The present V3 exact-namespace rule needs one entry per namespace and module; a reviewed manifest cannot silently discover new modules. A source/semantic detector remains necessary to cover unused project references, conditional code and source-only facts.

Published events are not synchronous Inbound adapters. Registry and Transaction event publication need separate mapping and message compatibility tests. IAM contract use includes authorization semantics; the adapter must not move or bypass the authoritative permission decision. `IFX.Platform.Context.Contracts` is a shared protocol dependency and requires a separate decision about whether Application may reference it; a rule for each module's **own** public Contracts does not answer that question. Before any policy tightening, review existing module-specific call paths, migrate all affected modules, test the behavior, and only then propose changes to `policy/layerguard.json` and CI as a separate change.
