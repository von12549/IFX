# Coding Guardrails 已确认原则

本目录保存后续执行 plan 的架构约束。详细背景、IFX 现状和未定实现细节见 [讨论记录](00-guard-architecture-discussion.md)。示例 `AI_CODING_GUARDRAILS.md` 只提供门禁分层思路，不是 IFX 的规则来源。

## 门禁阶段与职责

```text
规则与项目约束
  → Pre-Code 影响面识别
  → 编码中快速反馈
  → Post-Code 静态、构建及行为验证
  → Diff Guard 复核最终变更集
  → CI required checks 决定合入资格
```

普通变更在任务内记录简短的 Pre-Code 影响面摘要；跨模块、公共契约、数据库、认证/租户、消息或部署等高风险变更留下独立、可审查的决策记录。Agent 执行适用的本地检查，本地 hook 用于快速反馈；CI 在干净环境重跑必要检查并作为最终机械门禁。统一规则和结果契约，但保留专用 validator 与可并行的 CI 工作流。

Architecture Tests 是 Post-Code 和 CI 使用的一类检测器。LayerGuard 负责其可证明的静态项目与源码边界；编译器语义、契约行为、运行时、数据库和部署规则由各自检测器负责。每条规则都应标明权威来源、检测器、覆盖范围和盲区；未检测不等于通过。

## 可维护、可再生成的交付物

后续 plan 应交付完整的 `docs/guards/` 目录及顶层 `README.md`。Tech Stack、项目映射、Rule 等指定输入可手动编辑；README 指导 AI Agent 读取输入、验证、再生成、测试、检查 diff，并报告未覆盖或失败项。生成硬门禁所需的输入必须结构化且可校验；再生成过程应可重复、尽量幂等，CI 提供不改文件的漂移检查。

**首版范围固定为文档索引、规则覆盖矩阵和新门禁框架。** IFX 现有 `src/layerguard.json` 及 G03/G04/G05 的权威链保持现状（包括 G03 catalog 与其生成视图的校验关系）。首版通过项目绑定读取、校验和引用它们，不迁移、不复制、不覆盖。规则输入与现有权威冲突、规则无检测器或生成未完成时，必须明确报告，不能显示为通过。

通用骨架规定阶段、规则元数据、结果/证据格式和失败语义；IFX 绑定现有 LayerGuard、G03/G04/G05、数据库门禁。新项目填写自己的技术栈、项目映射和检测器绑定，复用同一架构。

规则输入格式、命令接口和具体验收项由后续执行 plan 设计。若将来要由文档生成 LayerGuard 或 Gate 权威策略，必须另立可审查的权威来源迁移，不属于首版。
