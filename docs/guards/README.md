# Coding Guardrails

This directory is the entry point for people and coding agents maintaining IFX guardrails. The [principles](principles/README.md) explain the decisions; the [execution plan](plans/01-coding-guardrails-execution.md) describes the rollout. The generated [rule index](generated/INDEX.md) and [coverage matrix](generated/COVERAGE_MATRIX.md) show the current declared coverage.

## Ownership of files

Edit `inputs/TECH_STACK.json` for languages and trusted command IDs, `inputs/PROJECT_MAP.json` for areas, owners, focused checks and risk paths, and `inputs/rules/*.json` for rule metadata. Edit `bindings/ifx.json` when a detector or CI job changes. `contracts/*.schema.json` define the input, decision, manifest and result interfaces. `decisions/*.json` are independent records for high-risk changes. `scripts/guards/` and `tests/guards/` are maintained code.

Only `generated/INDEX.md`, `generated/COVERAGE_MATRIX.md` and `generated/guard-manifest.json` are generated. Do not hand edit them. The generator reads and hashes existing policy authorities but never rewrites `src/layerguard.json`, `mcp/LayerGuard/baselines/plan05.json`, G03/G04/G05 sources, existing validators or existing workflows. Rule files that refer to those sources contain pointers and coverage limits, not replacement allowlists. The existing specialized gates remain separate CI checks.

## Agent workflow

1. Read this README, the principles, the relevant rule files, the referenced authority and the coverage matrix. For a planned change, run `pwsh scripts/guards/Invoke-CodingGuard.ps1 -Stage Pre -PlannedPaths path/one,path/two`. Pre reports owners, areas, rules, risks and suggested focused commands. It is an impact estimate, never code verification.
2. For high-risk paths, write a reviewable `decisions/<id>.json` using `contracts/decision.schema.json`. Its `affectedPaths` must cover each triggered path. Pass `-DecisionPath docs/guards/decisions/<id>.json` to Pre when needed. Existing ADRs may be linked in the record's plan; the record itself is still needed for machine association. Record an ordinary change summary in the task notes.
3. Modify only the authoritative input or implementation. Validate and regenerate with `pwsh scripts/guards/Invoke-GuardRegeneration.ps1 -Mode Generate`. Review the generated diff. Run `-Mode Check`; CI uses this read-only mode and fails on stale output.
4. Run `pwsh scripts/guards/Invoke-CodingGuard.ps1 -Stage Post -Scope Focused` for a targeted local check, or `-Scope Full` when the impact is uncertain or gate infrastructure changed. Full may take time because it invokes the existing gate scripts and frontend quality commands. Local hooks are advisory; a skipped check is reported `not-run` and is never a pass.
5. Run `pwsh scripts/guards/Invoke-CodingGuard.ps1 -Stage Diff -BaseRef <base-branch>` before review. Diff includes tracked worktree changes and untracked files locally. CI passes explicit base/head SHAs. Diff uses changed decision records by default; `-DecisionPath` can select a specific record. Use `-DeclaredPaths` with repository-relative globs to reject changes outside the declared scope in a local review. Diff checks only mechanical facts, including risk association, generated drift and protected deletions. Human reviewers still judge intent, test adequacy and policy changes.
6. Run `pwsh tests/guards/Test-CodingGuards.ps1` and the relevant existing gate. Inspect `artifacts/guards/*-result.json`, source reports and CI status. All new stage reports follow `contracts/guard-result.schema.json`; `blocked`, `fail` and `not-run` exit nonzero. The generated manifest is the command and rule input for the runner; rule prose is never executed.

The new `Coding Guardrails` workflow checks regeneration, Diff and the framework tests on pull requests, plus frontend lint/tests/build and compiled Domain assembly references in separate jobs. The Domain detector reads `src/layerguard.json` and checks actual direct assembly references after a Release build; it does not replace LayerGuard's project graph checks. Existing LayerGuard, G03/G04/G05, Plan 04 and database workflows retain their own authority and status. A green new workflow alone does not prove those gates passed. Branch protection must list the required checks; [rollout evidence](plans/02-implementation-evidence.md) records what was actually verified.

## New project

Use [templates/new-project/README.md](templates/new-project/README.md). Copy the three generic framework scripts and schemas, then fill in the template inputs and binding. The Domain assembly checker is an IFX-specific example and is optional for a new project. The default profile is `ifx`; for another project pass `-Profile <binding-file-stem>` to regeneration and each stage. The template fixture demonstrates a profile without IFX paths, module names or .NET commands. Adjust the project-specific CI workflow and CODEOWNERS; never mark a rule `full` until a positive and negative detector case prove it.
