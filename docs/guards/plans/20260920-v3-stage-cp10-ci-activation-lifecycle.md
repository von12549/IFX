# CP10 — CI activation lifecycle

This checkpoint implements Plan 06 P9 without switching the live workflow to a newly generated definition. V3 gains one stable deployment command with the lifecycle `Generate → Check → Preview → Install → Verify`; IFX supplies the lightweight workflow template, stable variables, required-check authority and activation mapping.

`Generate` writes only under `artifacts/generated/v3-ifx/activation/`. `Check` requires schema-valid inputs, byte-current candidates, a canonical workflow parse, the unchanged 13 check names/job dependencies/triggers, and a base-worktree first verdict entry. Validators are resolved by command ID and must be public. `Preview` treats the current headerless workflow and unmarked guard CODEOWNERS lines as `legacy-equivalent`, so the candidate can be compared in parallel without an activation switch. `Install` requires `-AcceptDeployment`; this checkpoint exercises it only in an isolated fixture. `Verify` requires the activated source path, composite SHA-256 and content to match.

`stages/ci/required-checks.json` replaces `ci/jobs.json` as the schema-validated authority for the ruleset, trusted-base activation, cost controls, change scope and 13 stable required checks. The active workflow reads that new base-owned path and adds the deployment lifecycle test, but its job names, DAG, triggers and verdict commands do not change. The remote verifier remains read-only and compares ruleset `23459908`, all required contexts, enforcement and strict mode. No remote rule or repository setting is written.

The CODEOWNERS guard lines are represented as a managed-block candidate. The real `.github/CODEOWNERS` stays unchanged in this checkpoint; a later separately authorized activation may review Preview and run Install. Positive and negative fixtures cover generation drift, malformed YAML, trusted-base first entry, explicit acceptance, source/hash verification, managed-block preservation, variable schema rejection, unbound tokens and non-public validators.
